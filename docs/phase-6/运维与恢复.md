# 运维、备份、恢复和升级

## 日常运行

工作数据在 /etc/archive-ledger.env 指定的 ARCHIVE_DB_PATH，数据库包含附件原文件、账号和日志；运行中的SQLite还可能使用同目录-wal和-shm文件。升级时保留整个数据目录，不复制单独的活动主数据库文件作为备份。

通过 systemctl status archive-ledger、journalctl -u archive-ledger 查看状态与程序错误；Nginx日志记录请求，业务操作日志在管理员页面。出现502先查应用健康检查和service日志；登录跳回登录页先查账号启用/授权变动与会话过期；上传被代理拒绝时核对Nginx的21m请求限制和应用20MB附件/10MB Excel限制。

服务以独立非特权用户运行，数据库目录700、备份文件600。日志与备份包含内部资料，使用公司既定的磁盘加密、访问管理和监控。应用不自动删除业务资料、日志或备份；定期检查磁盘余量及实际备份成功记录。备份应按公司策略再复制到异机存储，当前交付不配置未知的远程存储账号。

## 手工备份与校验

备份可在线执行；使用SQLite备份API读取一致快照，包含WAL中已提交的数据。成功后目录包含 archive.sqlite 和最后写入的 manifest.json。manifest不存在代表不完整，不用于恢复。

```bash
cd /opt/archive-ledger/current/backend
sudo -u archive-ledger /usr/bin/node scripts/maintenance.mjs backup --db /var/lib/archive-ledger/archive.sqlite --out /var/backups/archive-ledger
sudo -u archive-ledger /usr/bin/node scripts/maintenance.mjs verify --backup /var/backups/archive-ledger/实际备份目录
```

backup和verify均校验SQLite完整性、外键、结构版本、各表数量及每份附件的大小和SHA-256；verify额外比对整个快照的SHA-256和字节数。备份可能占用与数据库近似的空间，运行时间随附件数量增长。快照内含账号哈希及会话数据，应按工作数据保管；恢复会清除会话和登录失败计数，保留账号密码哈希、授权和操作日志。

## 恢复

工具始终拒绝覆盖现有数据库或残留WAL名称，要求全新路径。先校验，再停服务，先备份当前库，然后恢复到新文件、切换配置。原文件保留用于回退。

```bash
sudo systemctl stop archive-ledger-backup.timer
sudo systemctl stop archive-ledger-backup.service
sudo systemctl stop archive-ledger
cd /opt/archive-ledger/current/backend
sudo -u archive-ledger /usr/bin/node scripts/maintenance.mjs backup --db /var/lib/archive-ledger/archive.sqlite --out /var/backups/archive-ledger
sudo -u archive-ledger /usr/bin/node scripts/maintenance.mjs restore --backup /var/backups/archive-ledger/待恢复备份目录 --target /var/lib/archive-ledger/archive-recovered-20261110.sqlite
```

若当前库已损坏无法备份，保留原数据目录，由运维核对后继续恢复。新目标名称须按本次操作更换，不能重复使用示例名称。restore先验证备份，恢复后清除会话、记录数据库恢复事件，再验证新库。修改 /etc/archive-ledger.env 的 ARCHIVE_DB_PATH 指向新文件；后续定时备份也会使用该配置。

```bash
sudoedit /etc/archive-ledger.env
sudo systemctl start archive-ledger
curl --fail http://127.0.0.1:8080/api/health
node /opt/archive-ledger/current/deploy/linux/check-deployment.mjs https://实际内网域名
sudo systemctl start archive-ledger-backup.service
sudo systemctl start archive-ledger-backup.timer
```

所有使用者重新登录。核对档案数量、最近档号、附件下载及操作日志，再开放业务。计数器恢复到备份时间点，备份之后已发生的登记和纸质移交流转需人工核对并补录，避免把恢复时间点之后已经使用的档号再次分配给其他资料。

若需回退，停止应用，将 ARCHIVE_DB_PATH 改回保留的原库，重启并检查；不要混合不同数据库的主文件与WAL。恢复演练应使用新路径或隔离环境，不能用覆盖工作库来测试。

## 版本升级与回滚

新运行包解压到新的 releases/版本号 目录，校验包SHA-256及 tools/verify-release.mjs，保留旧版本。先做完整备份，停止定时备份和应用，再将current符号链接切换到已核实的新版本，保持数据路径不变，启动并执行健康检查、页面及权限抽查，最后恢复定时备份。升级前后记录版本和备份目录。

当前1.0.0的结构版本为3，能够增量初始化前期结构；遇到高于3的数据库版本会拒绝启动，避免误用旧程序。未来若升级改变结构，回滚需同时按该版本说明恢复兼容的备份，不能仅切回旧程序。实际切换命令由服务器管理员依据已确认的版本路径执行。

## 本机验证环境

开发电脑仍可使用前端5173/后端3001进行开发；生产试运行使用8080和同一工作库，验证前先停止3001实例，防止将开发操作写入正式试运行。正式服务器只启用一份应用服务。临时验收脚本均使用独立数据库，不修改工作库。
